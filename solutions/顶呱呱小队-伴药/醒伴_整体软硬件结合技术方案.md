# 醒伴（CareBox）整体软硬件结合技术方案

> 版本：V1.0（基于软件PRD链接、患者端/家属端Demo，以及《醒伴比赛样机硬件与固件PRD V1.0》）
> 日期：2026-10-16
> 定位：比赛样机联调与演示实施方案，不等同于量产、医疗器械注册或临床验证方案。

## 1. 方案结论

醒伴采用“**患者端微信小程序 + 家属端微信小程序 + 云端业务服务 + BLE/HTTPS设备接入 + ESP32-S3日仓与家庭主体**”的端云一体架构。

核心原则：

1. 日仓在具备有效时间、计划、供电和输出资格时，本地独立产生提醒，不依赖手机在线。
2. 开盖只形成“**开合推定**”证据，不表述为吞服证明、药品识别或患者清醒证明。
3. 家属端按事实分层显示：已收到开合推定、待核查、离线/数据过期、通知未送达。
4. 所有事件使用稳定设备身份、启动代次 `boot_epoch`、序号 `seq` 和内容摘要，支持幂等补传、冲突隔离和精确清理。
5. Demo中的“防漏服、分级追呼、远程安心、小睡联动”作为可演示业务流程；其中真实外呼、人体睡眠识别、实时远程闭环需显式标注联调中或后续能力。

## 2. 目标与比赛样机边界

### 2.1 交付目标

- 患者无需操作手机即可获得日仓本地提醒。
- 正常完整滑盖轨迹自动生成一次开合推定记录。
- 手机/主体/日仓恢复后，记录可回传并保留来源。
- 家属可以看到每日4次计划、已服/未完成/待核查、最近同步时间和异常事件。
- 对漏服和重复取药进行分级提示，不自动给出补服医学建议。
- 通过两只真实四格电子日仓 + 一个家庭主体完成现场演示；七日视图中的其余五仓为展示道具。

### 2.2 不纳入本次承诺

- 真实库存传感、自动识药、扫码识药的生产级闭环。
- 物理定时锁、儿童防护、人体睡眠/起身传感。
- 任何开盖都算服药。
- 手机录音、拾音器确认音箱已播放。
- 两个日仓同时独立4G在线、七仓独立充电/识别/灯控。
- 自动决定剂量、漏服补服方案或诊疗建议。

## 3. 总体架构

```text
患者端小程序                         家属端小程序
  ├─今日计划/倒计时                     ├─远程守护/今日进度
  ├─用药时间线                          ├─漏服升级/电话确认
  ├─设备与日仓                          ├─重复取药/风险事件
  └─设置与隐私                          └─家属权限/通知回执
           │ HTTPS / WebSocket / 订阅消息（按实际渠道能力）
           ▼
  API Gateway / 鉴权 / 幂等事件入口
           │
  业务服务：账户家庭、计划批次、提醒状态机、事件归档、库存估算、通知编排
           │
  PostgreSQL/Supabase + 对象/审计存储
           │
  Device Gateway：BLE控制、POD UART、HTTPS上行、4G附件会话
       ┌───┴────────────────────┐
  日仓A / 日仓B              家庭主体
  ESP32-S3 + RTC + LID       ESP32-S3 + 屏幕 + WS2812B-V6 + PCM5102/AUX
```

## 4. 关键数据流

### 4.1 正常服药

1. 云端下发或设备采用带版本的计划与装药批次。
2. 日仓校验实体身份、有效批次、目标格位、时间质量和计划状态。
3. 到点创建持久提醒实例，执行本地蜂鸣/振动；主体在通信成立时增强屏幕、灯光和音箱提示。
4. 读取五开关去抖后的完整轨迹：闭合 → 目标档稳定 → 闭合。
5. 日仓持久保存原始事件与推定依据，停止该实例未触发的重复提醒。
6. 手机/主体/4G恢复连接后按原事件ID补传；云端先落库再返回精确 durable receipt。
7. 家属端只显示有证据支持的状态。

### 4.2 漏服与分级追呼

- 到点：患者端与药盒灯语提醒。
- 未开盖：按配置进行有限次数、有限间隔重提。
- 达到期限：形成“提醒超时/未完成待核查”，不要与“设备失时”混用。
- 服务通知：推送患者与紧急联系人；渠道未达时显示未送达/待补偿。
- 电话追呼：先联系患者；患者未响应，再联系家属。真实自动外呼须以渠道联调结果为准。
- 迟到开盖：更新同一提醒实例，保留漏服/超时历史，不改写原始事实。

### 4.3 重复取药

1. 对比上一次有效开合记录与安全间隔。
2. 间隔内开盖不自动判定再次服药，记录风险事件。
3. 患者端给出风险提示；家属端收到待确认事件。
4. 家属可一键电话确认；确认结果作为追加人工记录，不覆盖设备原始事实。

## 5. 端云职责

| 层级   | 主要职责                     | 关键边界                    |
| ---- | ------------------------ | ----------------------- |
| 患者端  | 今日计划、倒计时、提醒设置、设备状态、历史、隐私 | 不把蓝牙重连直接当作睡醒；不自动建议补服    |
| 家属端  | 进度、异常、漏服升级、风险事件、权限、电话入口  | 展示来源/时间/新鲜度；不把模拟状态当真实回执 |
| 云端   | 家庭账户、计划批次、事件幂等、通知编排、审计   | 不先ACK后入库；同ID异内容冲突隔离     |
| 日仓固件 | 本地时钟、计划、提醒、滑盖轨迹、离线存储     | 开盖是推定证据；失时不运行猜测药程       |
| 家庭主体 | 供电、POD通信、屏幕、在家声光增强       | 两颗LED不映射七个独立格位          |
| 共享4G | 当前所接日仓离站上行               | 切换会话必须隔离设备身份和旧响应        |

## 6. 统一状态模型

### 6.1 设备状态

`initializing`、`ready`、`clock_hold`、`maintenance`、`offline`、`syncing`、`low_battery`、`output_hold`、`storage_pressure`、`needs_review`。

### 6.2 提醒状态

`scheduled` → `due` → `reminding` → `completed_inferred` / `timeout_pending_review` / `missed_recorded`；迟到开盖为同一实例的追加状态，不新建重复服药记录。

### 6.3 事件来源

`device_inferred`（设备轨迹推定）、`patient_reported`、`family_confirmed`、`system_notification`、`demo_simulated`。UI必须显示来源。

## 7. 接口与数据合同

逻辑数据组：

- 身份：`device_id`、`producer`、`slot`、`accessory_id`、`session_id`
- 配置：`plan_version`、`fill_batch_id`、`adopted_at`、`effective_at`
- 提醒：`occurrence_id`、`target_cell`、`due_at`、`expires_at`、`repeat_policy`
- 事件：`boot_epoch`、`seq`、`event_type`、`evidence`、`digest`
- 时间：`occurred_at`、`time_quality`、`monotonic_ms`、`time_source`、`correction`
- 库存：`cell_counts`、`quantity_mapping`、`revision`、`source`
- 同步：`local`、`relay`、`durable`、`conflict`、`disposition`

关键API建议（具体字段以现有typed codec和生产代码为准）：

| API                               | 用途          | 幂等键                              |
| --------------------------------- | ----------- | -------------------------------- |
| `GET /v1/devices/:id/state`       | 读取设备多维状态    | -                                |
| `POST /v1/devices/:id/events`     | 上报原始事件      | `producer+boot_epoch+seq+digest` |
| `POST /v1/plans`                  | 创建计划草稿      | `client_request_id`              |
| `POST /v1/plans/:id/adopt`        | 采用计划/批次     | `plan_version+fill_batch_id`     |
| `POST /v1/notifications/dispatch` | 编排服务通知/电话任务 | `occurrence_id+escalation_level` |
| `GET /v1/families/:id/timeline`   | 双端时间线       | -                                |
| `POST /v1/events/:id/corrections` | 追加纠正        | `correction_id`                  |

> 上述REST是业务层建议，不替代现有固件typed操作、既有HTTPS服务、证书和正式回执材料；在联调前必须由后端负责人确认实际路径。

## 8. 安全、隐私与合规

- BLE采用安全配对与会话鉴权；旧会话、旧回调和旧权限必须失效。
- 家属角色至少区分：紧急联系人（接收异常推送）与仅查看家属。
- 锁屏通知默认脱敏：只显示“到点用药啦，记得开盖取药”。
- 诊断材料不得对外暴露PIN、密钥、完整Flash/NVS和患者身份。
- 云端审计保留原始事实、纠正记录、通知层级、查看和处理时间。
- 任何“已服”文案建议使用“已开盖，形成开合推定”；Demo若保留“已服”，需加说明。

## 9. 联调与验收门槛

P0优先顺序：

1. 身份、启动代次、断电恢复和安全通信。
2. 时间质量、计划采用、整仓换装和精确回读。
3. 五档滑盖去抖、完整轨迹只生成一次推定。
4. 离线记录、补传、幂等和冲突隔离。
5. 家属端状态来源、新鲜度和通知证据。

P1：主体屏显、声光增强、共享4G、余量估算、回站检查。

必须执行T01-T20验收矩阵；验收记录至少包含版本、设备、条件、操作、原始证据、结果和未覆盖项。蜂鸣/ERM、机械、续航、主体与两仓联调当前均不能按“已通过”表述，需以同版实测记录为准。

## 10. 演示脚本建议

1. 患者端展示08:00已完成、12:00倒计时、18:00/22:00待服。
2. 倒计时归零，药盒灯语与本地提示启动。
3. 正常滑盖完成，患者端显示开合推定，家属端静默收到回执。
4. 模拟12:00未开盖，展示三次重提、漏服记录、患者追呼、家属兜底。
5. 模拟安全间隔内再次开盖，展示重复取药风险事件与一键电话确认。
6. 展示设备离线、最后同步、待核查，不把离线直接判漏服。
7. 最后展示七日视图，并明确“两真五道具”。

## 11. 版本与风险

- 固件基线：paired-r7，ESP-IDF 5.4.2；具体APP身份与哈希以原硬件PRD第15章为准。
- 当前高风险：稳定免PIN重连、RTC与真实计划闭环、蜂鸣/ERM输出、两仓主体联调、真实通知/外呼、日志容量、机械和24小时续航。
- 任何原型动画、模拟按钮或Coze页面均只能作为交互证据，不得替代实板、服务端和端到端验收。
