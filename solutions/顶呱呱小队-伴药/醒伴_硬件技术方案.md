# 醒伴（CareBox）硬件与固件技术方案

> 版本：V1.0｜依据：《醒伴比赛样机硬件与固件PRD V1.0》（2026-10-14）｜用途：比赛样机联调与验收

## 1. 硬件方案结论

比赛样机采用：

- 两只真实电子日仓，每只四格、五档滑盖检测。
- 一个家庭主体，提供供电、POD有线通信、屏幕、在家声光增强。
- 一个在两只日仓之间受控轮换的共享4G附件。
- 手机通过BLE与设备控制/读回；云端通过HTTPS接收业务事件和下发受控操作。

本方案以“**设备本地提醒 + 有来源开合证据 + 断网可恢复 + 云端幂等归档**”为技术主线。当前蜂鸣器/ERM、完整主体与两仓闭环、稳定免PIN重连、RTC/真实计划闭环、机械和续航均须实测，不得把候选实现写成已验收。

## 2. 硬件组成

### 2.1 日仓

| 模块      | 当前基线                          | 技术职责                           |
| ------- | ----------------------------- | ------------------------------ |
| 主控      | ESP32-S3-MINI-1-N8            | BLE、WiFi候选、本地状态机、持久化、8MB Flash |
| RTC     | PCF8563T + 32.768kHz晶体        | 保时、时间质量检查；无独立后备电源              |
| 充电电源    | ETA6003Q3Q                    | 按冻结电路和实测充电行为验证                 |
| 变换/开关   | TPS63802、TPS2559              | 电源与附件供电路径                      |
| 接口保护    | SN74LVC1G125、TMUX1511、TXU0202 | 对接、采样隔离                        |
| 辅助电源/温度 | GX112S、TPS70933               | 按冻结电路用途使用                      |
| 滑盖检测    | 5×SPVS310100 + 六线LID板         | 闭合、四目标档、过渡/异常                  |
| 输出      | MLT-8530蜂鸣器、ERM驱动             | 当前实板输出准入HOLD                   |
| 显示      | 约40×15×4mm，横向160×80坐标         | 显示时间、下一提醒、格位、状态                |

注意：BASE930、DAY982是项目对象/命名，不是MCU型号。器件型号不能替代电源、电流、温升、ADC、保护和续航实测。

### 2.2 家庭主体

- 主控：ESP32-S3-MINI-1-N8。
- 输入：5V Type-C。
- 电源：SY8089AAAC。
- 对接：三路TX/RX缓冲，具体针序以冻结原生电路和配对表为准。
- 屏幕：无触摸操作准备；TTP223仅用于低亮唤醒查看，不作为服药确认按钮。
- 声音：PCM5102 + AUX外接有源音箱。
- 外灯：两颗WS2812B-V6；不等同于七格独立灯控。

### 2.3 电池和共享4G

- 日仓使用受保护可充电锂电池。
- 电池包络输入约52×34×5.2mm；完整电池、保护板、线束和连接器仍需核实。
- CT12-C(T1)共享4G附件由当前所接日仓供电，工程约束为3.4-4.5V、约至少1.2A能力并叠加日仓负载。
- 满电离站24小时是验收目标，必须对两只真实日仓逐只执行带4G/不带4G两种工况测试。
- 共享附件切换前停止会话、处理在途状态、关闭输出并隔离数据；附件身份和日仓身份分开。

## 3. 连接拓扑

```text
手机 ──BLE安全会话── 日仓
                    │
                    ├─POD UART──家庭主体──屏幕/两颗灯/PCM5102+AUX
                    ├─WiFi候选──HTTPS──云端
                    └─共享4G（当前所接日仓）──HTTPS──云端
```

边界：

- 未实现“主体作为BLE Central无线转发给日仓”。
- 主体联网不代表离站日仓获得网络。
- 现有网络实现采用HTTPS，不宣称已有MQTT。
- J DEBUG为维护下载接口，不是患者使用入口，也不自动等同日常充电口。
- J DEBUG约定：1 GND、2 P3V3、3 USB DM PORT、4 USB DP PORT、5 BOOT N、6 CHIP EN、7 DEBUG TX、8 DEBUG RX；3.3V TTL和共地条件必须按受控调试流程执行。

## 4. 固件架构

```text
Boot / Recovery
  ├─身份与boot_epoch恢复
  ├─NVS/Flash完整性检查
  ├─RTC与时间质量检查
  └─外设资格检查

Application State Machine
  ├─PlanManager：计划/版本/有效期
  ├─FillBatchManager：维护/整仓换装/批次
  ├─ClockManager：RTC/校时/ClockHold
  ├─LidTracker：五触点去抖/轨迹
  ├─ReminderScheduler：提醒实例/重提/升级
  ├─EvidenceStore：原始事件/摘要/离线队列
  ├─SyncManager：BLE/POD/WiFi/4G/HTTPS
  ├─OutputManager：蜂鸣/振动/屏/灯/音箱
  └─Diagnostics：STATUS/STACK/BLE/CFG/TRACE
```

固件基线：ESP-IDF 5.4.2，paired-r7；主栈调整至8192字节并保留栈守卫。当前诊断存在，不代表登记、认证、恢复和产品闭环已修复。

## 5. 本地状态和持久化

必须分别持久化：

1. `device_id`、`producer`、槽位、附件和会话身份。
2. `boot_epoch`，保证重启后新事件身份不撞号。
3. 计划版本、装药批次、采用状态和有效时间。
4. RTC时间、时间质量、校时来源、校时年龄与误差状态。
5. 提醒实例、重提次数、期限和已发出的升级历史。
6. 原始开合轨迹、时间、单调计时、依据和摘要。
7. 库存人工登记、映射、revision和审计摘要。
8. 未获云端精确持久回执的离线事件队列。

掉电/重启规则：完整有效且校验通过的状态才可恢复；不完整事务进入待核查；不能自动全擦、重登记或用旧镜像掩盖故障。

## 6. 时间质量

设备必须区分：

- `trusted`：有有效校时和可接受误差预算。
- `stale`：可保时但校时过久或精度下降。
- `unknown`：重启后无法证明校时年龄/连续性。
- `invalid`：RTC读写失败、VL风险、归零/冻结/明显跳变。

检查时机：启动、校时、重连、每次提醒前、MCU独立周期复核。失时或无法判断窗口时进入ClockHold，不执行猜测药程；校时成功后也不重放已完成提醒、不自动建议补服。

## 7. 五档滑盖和服药推定

### 7.1 输入处理

- 读取五个SPVS310100开关。
- 对波形进行去抖，识别闭合、格1-4稳定档、过渡和异常。
- 中间档经过不生成事件。
- 多开关同时有效、卡住、预开未关、掉电中断均进入待核查。
- 更深滑动暴露前格，不能把多个可见格推导为多次服药。

### 7.2 有效完成条件

仅当同时满足：

- 存在有效提醒实例。
- 目标计划、批次、格位和窗口有效。
- 非维护状态。
- 出现新的“闭合 → 目标稳定档 → 闭合”完整轨迹。
- 最大稳定开放档就是该实例目标格。

才写入“已开合，开合推定”记录，并停止该实例未触发的重提/升级。关闭声音不等于完成；任意开盖不等于完成。

## 8. 提醒与输出

### 8.1 本地提醒

在有效计划、有效时间、供电和输出资格都成立时，到点在日仓本地触发蜂鸣和振动；不依赖手机或在线服务器即时命令。

### 8.2 家庭主体增强

主体根据真实识别的槽和提醒实例进行屏、灯、音箱提示；两仓同时触发时按实例排队，完成一仓只取消自身任务。

现行灯语建议：

| 灯色  | 含义            |
| --- | ------------- |
| 橙色  | 到点提醒          |
| 黄色  | 重复提醒中         |
| 深橙红 | 漏服/异常，需核查     |
| 绿色  | 本次形成开合推定，短时确认 |
| 白色  | 待机            |
| 蓝色  | 连接/同步         |

但实物为两颗WS2812B-V6，不能宣称七路独立格灯。蜂鸣/ERM当前HOLD，演示前需人工试播并记录供电、音量、AUX、首播、连续播放和两仓并发。

## 9. 设备控制接口

沿用现有typed操作语义，不在本方案虚构新固件协议：

1. 读取状态。
2. 进入维护。
3. 采用有限计划。
4. 采用周计划。
5. 显式UTC校时。
6. 精确校时请求恢复。
7. 历史校时请求检查。
8. 取消周计划。
9. 空白设备首次登记。
10. BASE时间租约。
11. 人工装药库存登记。
12. 人工数量纠正。
13. 仅改未来提醒时间。
14. 独立确认后恢复原计划。
15. 库存审计分块读取。
16. 已收到并核验库存审计轮换。

约束：u64身份和版本使用十进制字符串；UTC秒/毫秒不可混用；请求分片和SHA使用真实typed字节；回执必须属于当前请求和连接代次；断链或超时先读回，不盲目重发。

## 10. 整仓换装流程

1. 设备确认进入维护，并持久回读。
2. 人工清空日仓并核对。
3. 建立新装药批次，录入四格数量与人工药品资料。
4. 写入计划与目标格，提交采用请求。
5. 精确读取设备持久状态，确认批次、版本和计划一致。
6. 事务完成后退出维护。

只支持整仓重新装药；部分补药、跨格换药、自动识药、真实库存传感不属于本次能力。中断时保持待核查，不自动回滚旧药程，也不把未来时间编辑伪装成换装。

## 11. 网络、同步和事件合同

事件完整身份：

```text
producer + device_id + boot_epoch + seq
```

原始内容必须包含：事件类型、格位/轨迹、发生UTC或null、单调时间、时间质量、计划批次和证据。发送、接收、中继、重试元数据不参与原始摘要。

处理规则：

- 同ID同规范化内容：幂等返回原内容确认。
- 同ID异内容：两份保留、摘要冲突、受影响业务待核查。
- 云端先归档后回执，禁止先ACK后落库。
- 丢确认时重发原ID和原内容，不新造事件。
- 日仓、主体、手机和4G都必须保留原生产者和来源，不把中继设备冒充事件生产者。

## 12. 故障与降级

| 故障    | 设备行为            | App文案        |
| ----- | --------------- | ------------ |
| RTC无效 | ClockHold，不运行药程 | 设备时间不可确认，待校时 |
| 无网    | 本地继续；事件入队       | 设备离线，最后同步时间  |
| 日仓低电  | 提示低电，保持事实记录     | 电量低，可能影响后续提醒 |
| 日志接近满 | 提示存储压力，禁止静默覆盖   | 需要尽快回站同步     |
| POD断链 | 日仓/主体状态分开       | 日仓可用/主体离线    |
| 音箱断电  | 不伪报已播放          | 外音箱输出待核查     |
| 滑盖错档  | 保留轨迹，待核查        | 未形成有效开合推定    |
| 4G切换  | 停会话、隔离在途数据      | 当前日仓4G会话切换中  |

## 13. 硬件验收计划

必须按版本、设备、条件、操作、证据、结果、未覆盖项记录：

- T01：两仓换槽/改星期，身份不变，历史不串。
- T02：重启/掉电，boot_epoch和状态可恢复。
- T03-T04：正常换装与掉电/旧回执，批次不回滚、不重复。
- T05-T07：无手机无网提醒、输出故障降级、主体双仓并发。
- T08-T10：正确/错档/深开/抖动/超时升级/迟到完成。
- T11-T16：纠正、冲突、补传、日志压力、校时归零/回拨。
- T17-T20：4G换仓、电量与24小时、权限撤回、版本恢复。

声音至少覆盖：正常供电、长待机首次、连续播放、两仓并发、静音、断电、拔AUX。机械需覆盖四格包络、盖运动、脱盖、倒置撒落、装配维修、连接器对准和线束。续航必须记录网络条件、弱信号、带4G/不带4G和功能退出点。

## 14. 当前待闭合项

1. 稳定免PIN重连和认证/订阅顺序。
2. 一只真实日仓的校时、计划、开合推定、取消恢复闭环。
3. 第二只日仓与家庭主体联调。
4. 蜂鸣器/ERM实际输出资格与可听感。
5. 屏幕“最近服药时间”常显差距与功耗。
6. 电池、共享4G峰值供电、温升和24小时续航。
7. LID制造输入、机械保持、线束/电池包络。
8. 正式HTTPS服务、通知、短信和电话回执。
9. 日志容量、冲突清理和掉电事务恢复。

## 15. 后续产品化方向

- 七只真实电子仓与整机供电/容量验证。
- 物理时间锁和机构级防重复方案。
- 人体睡眠/起身检测并验证误报边界。
- 声音反馈诊断能力（必要时重新论证拾音成本）。
- 药品识别和精确药量传感。
- 手机免串口配网、换机与账户恢复。
- 家属真实推送、一键拨号、自动外呼和失败处理。
- 单手防撒、长期携带、儿童防护和患者共创验证。
- 部分补药、复杂周期、更多剂型及长期真实使用验证。
