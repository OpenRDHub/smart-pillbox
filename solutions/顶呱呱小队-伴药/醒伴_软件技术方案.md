# 醒伴（CareBox）软件技术方案

> 版本：V1.0｜目标：比赛样机软件联调、Demo演示与后续真实设备接入

## 1. 软件方案结论

软件采用“双微信小程序 + 云端业务服务 + 设备接入层”的模块化架构：患者端负责低打扰自我管理，家属端负责远程安心与异常兜底，云端负责事实归档、状态机、通知编排和权限审计，设备接入层负责BLE/POD/HTTPS/4G数据转换。

建议技术栈：

| 层       | 比赛样机建议                                | 赛后升级                         |
| ------- | ------------------------------------- | ---------------------------- |
| 患者端/家属端 | 微信小程序原生或Taro + TypeScript             | 视数据规模迁移跨端壳或原生App             |
| UI      | React/Taro或小程序组件 + Design Tokens      | Storybook/统一组件库              |
| 云端API   | Node.js + TypeScript + NestJS/Fastify | 微服务按设备、通知、账户拆分               |
| 数据库     | PostgreSQL/Supabase                   | 云RDS/读写分离/时序归档               |
| 实时同步    | Supabase Realtime/WebSocket           | 独立WebSocket Gateway + MQ     |
| 设备接入    | BLE GATT、POD UART转发、HTTPS             | Device Gateway + MQTT仅在评估后引入 |
| 通知      | 微信订阅消息 + 短信兜底；电话接口待联调                 | 正式消息供应商、外呼服务、回执聚合            |
| 部署      | Supabase Edge Functions/Node服务 + CDN  | 容器化、灰度、可观测性平台                |
| 测试      | Vitest/Jest、Playwright、小程序真机          | 设备农场、契约测试、混沌与离线测试            |

> 当前硬件PRD明确：现有网络实现采用HTTPS，不声称已有MQTT；因此不要在比赛版文档中把MQTT写成已实现。

## 2. 信息架构

### 2.1 患者端

- 首页：问候、设备在线、下一次服药、今日进度。
- 今日计划：时间线、倒计时、格位、上次开盖时间、提醒状态。
- 记录：日/周/月统计、按时/补服/漏服/待核查、原始事实与业务推定分开。
- 设备：日仓、家庭主体、蓝牙、4G附件、电量、固件、同步状态。
- 计划：药物资料、时段、目标格、重复规则、重提策略、安全间隔。
- 我的：个人资料、家属共享、隐私、提醒方式、库存估算、演示重置。

### 2.2 家属端

- 守护首页：被守护人、今日进度、最后同步、数据新鲜度。
- 动态：已收到回执、风险事件、漏服升级、查看/协助记录。
- 事件详情：发生时间、设备来源、证据层级、通知渠道、当前处理状态。
- 电话确认：一键联系患者；患者无响应时再联系紧急联系人。
- 家庭成员：紧急联系人、仅查看、邀请、撤权。

## 3. 前端状态管理

推荐使用 `TanStack Query` 管理服务端状态，轻量本地状态使用Zustand或小程序Store。

```text
Server state
  ├─ family / patient
  ├─ todayOccurrences
  ├─ deviceSnapshot
  ├─ timelineEvents
  └─ notificationReceipts

Local state
  ├─ currentTab
  ├─ demoScenario
  ├─ pendingBleSession
  ├─ offlineOutbox
  └─ privacySettings
```

状态更新必须带 `updated_at`、`source`、`freshness`。客户端不得用本地按钮直接把设备事件写成“已服”。Demo按钮只能创建 `demo_simulated` 事件或切换演示时钟。

## 4. 领域模型

```ts
interface DeviceIdentity {
  deviceId: string;
  producer: "day" | "base";
  slot?: number;
  accessoryId?: string;
  sessionId?: string;
}

interface Occurrence {
  id: string;
  planVersion: string;
  fillBatchId: string;
  targetCell: 1 | 2 | 3 | 4;
  dueAt: string;
  expiresAt?: string;
  status: "scheduled" | "due" | "reminding" | "completed_inferred" | "timeout_pending_review" | "missed_recorded";
  source: "device_inferred" | "patient_reported" | "family_confirmed" | "demo_simulated";
}

interface DeviceEvent {
  producer: string;
  deviceId: string;
  bootEpoch: string;
  seq: string;
  type: "lid_transition" | "lid_trajectory" | "reminder" | "sync" | "diagnostic";
  occurredAt: string | null;
  monotonicMs: number;
  timeQuality: "trusted" | "stale" | "unknown" | "invalid";
  evidence: Record<string, unknown>;
  digest: string;
}
```

## 5. 数据库设计

核心表：

- `accounts`：账户与登录身份。
- `families`、`family_members`：家庭关系和角色权限。
- `patients`：患者基础信息，健康信息最小化存储。
- `devices`：设备身份、产品角色、固件、绑定状态。
- `device_sessions`：BLE/4G/主体会话，不与设备身份混用。
- `medications`：药品资料与人工录入信息。
- `medication_plans`：计划草稿、版本、有效期、重复规则。
- `fill_batches`、`fill_cells`：整仓换装批次、四格数量和核对记录。
- `occurrences`：提醒实例和业务状态。
- `device_events`：不可变原始设备事件，唯一键为生产者+epoch+seq+digest。
- `event_corrections`：人工纠正追加记录。
- `notification_jobs`、`notification_receipts`：通知任务和渠道回执。
- `risk_events`：重复取药、设备离线、数据过期等风险事件。
- `audit_logs`：权限、查看、处理、设备命令和数据变更审计。

### 5.1 RLS与权限

- 患者可读写自己的计划、设置和人工纠正申请。
- 紧急联系人可读患者授权范围，接收漏服/风险通知。
- 仅查看家属只读记录，不接收异常推送。
- 设备写入只允许匹配绑定实体、当前会话和合法事件身份。
- 家属不能修改设备原始事件，只能追加确认或纠正。

## 6. API分层

### 6.1 账户与家庭

- `POST /auth/wechat/login`
- `GET /families/:familyId`
- `POST /families/:familyId/invitations`
- `PATCH /family-members/:id/role`
- `DELETE /family-members/:id`

### 6.2 计划与装药

- `POST /plans/drafts`
- `POST /plans/:id/adopt`
- `POST /fill-batches`
- `POST /fill-batches/:id/confirm`
- `PATCH /plans/:id/future-occurrences`

计划采用与服务器收到、设备持久采用、实际生效必须分层返回：

```json
{
  "request_id": "req_123",
  "server_received": true,
  "device_adopted": false,
  "effective": false,
  "durable_receipt": null,
  "needs_review": false
}
```

### 6.3 事件与同步

- `POST /devices/:deviceId/events/batch`
- `GET /devices/:deviceId/sync-state`
- `POST /devices/:deviceId/commands`
- `POST /events/:eventId/corrections`
- `GET /occurrences/:id/timeline`

事件接收必须：验证身份 → 规范化 → 计算摘要 → 幂等查询 → 冲突隔离或落库 → 生成精确回执。HTTP 200不能直接代表业务已持久化。

## 7. 提醒状态机

```text
scheduled
   ↓ due
reminding ──有效轨迹──> completed_inferred
   │
   ├─有限重提仍无轨迹──> timeout_pending_review
   │                         ↓升级
   │                    missed_recorded
   │
   └─设备离线/时间未知──> needs_review
```

约束：

- 重提任务按 occurrence_id 工作，不因重启或抖动续期。
- 漏服后迟到开盖更新同一实例，保留超时历史。
- 不因午夜自动把未处理实例判为漏服。
- 设备失时与提醒超时使用不同枚举和文案。
- 安全间隔内开盖为风险事件，不直接生成第二次完成。

## 8. Demo到真实能力映射

| Demo能力 | 软件落地方式                  | 真实能力边界          |
| ------ | ----------------------- | --------------- |
| 防漏服倒计时 | 服务端/本地演示时钟 + occurrence | 真实时间由设备时间质量决定   |
| 分级追呼   | 通知编排状态机                 | 自动电话和短信需渠道实测    |
| 远程安心   | 家属订阅实时事件/轮询             | 展示最后同步和数据新鲜度    |
| 重复取药   | 安全间隔规则 + risk_event     | 不做物理锁，不做补服建议    |
| 小睡联动   | P1演示场景                  | 无人体传感，不能称自动识别睡眠 |
| 库存预警   | 人工装药数量 - 计划消耗           | 不是传感器精确库存       |
| 七日仓    | 计划视图                    | 两真五道具，不是七台在线设备  |

## 9. 离线与可靠性

客户端：

- 读缓存可展示最近状态，但必须标记 `last_synced_at`。
- 写操作进入本地outbox，使用请求ID重试。
- 不在客户端本地伪造设备完成状态。

服务端：

- 事件表不可变；纠正另表追加。
- 同ID同摘要幂等；同ID异摘要冲突隔离。
- 通知任务与事件归档解耦，通知失败不能回滚事实。
- 数据过期、渠道未送达、设备离线分别建状态。

## 10. 可观测性与测试

指标：

- 设备事件落库成功率、重复事件率、冲突率。
- 事件从发生到家属端可见的延迟。
- 通知发送/接收/查看/处理各层回执。
- 离线时长、补传成功率、日志压力。
- 计划采用与 durable readback 成功率。

测试：

- 单元：状态机、时间窗口、安全间隔、幂等、冲突。
- 契约：typed codec与API字段、u64字符串、UTC秒/毫秒。
- E2E：正常开盖、错档、预开未关、断电、重启、乱序ACK、离线补传。
- 真机：BLE权限、后台、微信订阅消息、弱网、设备切换。
- Demo验收：四条流程必须能从患者端和家属端同步呈现，模拟数据标记清晰。

## 11. 软件实施顺序

### Phase 1：演示闭环

实现固定测试药程、今日时间线、倒计时、正常开盖、漏服升级、重复取药、家属守护四条Demo链路；保留 `demo_simulated` 标记。

### Phase 2：真实设备闭环

接入设备状态、计划回读、开合原始事件、离线补传、幂等回执；先闭合一只真实日仓，再扩展第二只。

### Phase 3：可信通知与权限

完善微信订阅消息、短信兜底、电话渠道回执、家庭邀请撤权、数据新鲜度和审计。

### Phase 4：产品化

云端服务拆分、可观测性、灰度升级、设备农场、正式隐私政策和长期可靠性验证。
